RepoMind 2.0 — Corrected Architecture & Flow

1. What was wrong in the current design

  1. No POST /organizations endpoint — your flow assumed org creation happens "somewhere" during bootstrap/onboard. It shouldn't. Bootstrap should create only the first ORG_ADMIN user; org creation is a separate, explicit step so an admin can later create additional orgs.
  2. No PUT/POST decision endpoint distinct from approve — you only had approve. You need three outcomes: APPROVE, REQUEST_CHANGES, REJECT, each triggering a different downstream path.
  3. No merge endpoint — approval and merge are two different actions. Merge should be its own endpoint, auto-triggered by policy or manually invoked.
  4. "Installing a GitHub App on user desktops" is a misunderstanding to clear up — a GitHub App is never installed on a desktop; it's installed at the org/repo level on GitHub's website by an admin, and then it acts as a bot identity server-side. Since you explicitly don't want a bot identity doing merges, the correct model for you is per-user GitHub OAuth (not a GitHub App) — every human links their own GitHub account once, and every GitHub-side action (review, approve, merge) is executed using that specific person's OAuth token, so GitHub's own audit log shows the real human, not a bot. This is the model used below.
  5. No branch/commit-level endpoints — needed for the PR UI and for the SHA-staleness logic you already have conceptually.
  6. No chat history / session listing endpoints.

  • Organization = a company/tenant. Hard data-isolation boundary (RAG, findings, chat all scoped here).
  • Team = optional sub-grouping inside an org (e.g. "Payments Team"). Used for assigning reviewers and scoping dashboards for Team Leads.
  • Project = a logical folder of repositories (e.g. "Checkout Service" project containing api, worker, frontend repos).
  • Repository = one connected GitHub repo.
  • Below that: PRs, Review Runs, human decisions, chat sessions, and the event timeline all hang off the repository.

3. Identity Model: RepoMind User ↔ GitHub Identity

Two separate identities, explicitly linked — never assume they're the same person implicitly:

Table Purpose
users RepoMind login identity: email, password hash, org membership, role
github_credentials 1:1 link from a user to their GitHub account: github_user_id, github_username, encrypted OAuth access_token + refresh_token, granted scopes, linked_at
organization_github_installation (optional, org-level) Which GitHub org/repos this RepoMind org is authorized to see — used only for listing repos to connect, not for taking actions

Rule: a user cannot connect a repo, approve a PR, or trigger a merge on GitHub until their github_credentials row exists. RepoMind enforces this at the API layer — if missing, the endpoint returns 403 GITHUB_IDENTITY_NOT_LINKED and the frontend redirects to /oauth/login.

Auth + Identity Linking Sequence

    GH-->>API: GET /oauth/github/callback?code=...

    API-->>D: redirect to dashboard, identity linked

4. Roles & What Each Role Actually Does

Role Scope Can do
ORG_ADMIN Whole org Create org, invite members, assign roles, connect repositories, set merge policies, view Global Security Browser, manage org-level GitHub app-installation-listing token
TEAM_LEAD Assigned projects/teams Manage members within their team, assign reviewers to repos, view team-scoped analytics, cannot change org-wide settings
DEVELOPER Repos they have GitHub access to Open/view PRs, trigger AI review, use PR Chat, see findings on their own PRs, cannot approve/merge
REVIEWER Assigned repos Everything a Developer can do, plus: make the APPROVE / REQUEST_CHANGES / REJECT decision, trigger merge (if policy allows)

A user is invited into an org by an ORG_ADMIN (POST /organizations/{org_id}/members), given a role, and separately links their own GitHub identity. RepoMind never assumes GitHub permissions — it checks both: (a) RepoMind role allows the action, and (b) the linked GitHub token actually has permission on that repo (validated live via GitHub API on first connect, cached, re-validated on 403).

Dashboards by role

  • Org Admin Dashboard: org-wide PR volume, repos list, pending invites, Global Security Browser (all orgs' repos' open findings by severity), merge policy config, member list with roles.
  • Team Lead Dashboard: their team's repos, open PRs needing review, reviewer workload, team-scoped risk trend chart.
  • Developer Dashboard: "My PRs" (open/merged/rejected), findings needing my attention, recent chat sessions.
  • Reviewer Dashboard: review queue (PRs with a completed AI review awaiting human decision), history of my past decisions, stale-review alerts.

5. Repository Connection (No GitHub App, OAuth-only)

sequenceDiagram
    participant A as Org Admin
    participant API as RepoMind API
    participant GH as GitHub

    A->>API: GET /organizations/{org_id}/github/repos (uses A's linked token)
    API->>GH: list repos A has admin access to
    GH-->>API: repo list
    API-->>A: repo list to choose from
    A->>API: POST /repositories/connect {project_id, github_owner, github_name}
    API->>GH: create webhook (pull_request, push, pull_request_review) using A's token
    GH-->>API: webhook created
    API->>DB: save repository row + webhook_secret
    API-->>A: repository connected

Webhook delivery secret is verified on every incoming event (X-Hub-Signature-256). No GitHub App, no desktop install — just a webhook created via the connecting admin's OAuth token with admin:repo_hook scope.

6. PR Ingestion → AI Review

sequenceDiagram
    participant GH as GitHub
    participant WH as RepoMind Webhook Handler
    participant DB as PostgreSQL / pgvector
    participant LLM as Gemini

    GH->>WH: webhook: pull_request opened/synchronize
    WH->>DB: upsert pull_request (head_sha, base_sha, branches, status=OPEN)
    WH->>DB: mark prior review_runs for this PR as STALE (if head_sha changed)
    Note over WH: Developer or auto-trigger calls review
    WH->>GH: fetch diff, files, commits
    WH->>DB: retrieve top-k repo-rule chunks (pgvector) for changed files
    WH->>DB: fetch latest lint output
    WH->>LLM: diff + retrieved rules + lint results
    LLM-->>WH: structured findings (NEW/PERSISTENT/RESOLVED vs prior run)
    WH->>DB: save review_run + findings, status=COMPLETED

Findings are classified against the previous review run on the same PR (not just created fresh each time), which is what makes "NEW / PERSISTENT / RESOLVED" meaningful.

7. Human Decision → Merge (the part you're expanding)

Three decision outcomes, each with a distinct downstream path:

sequenceDiagram
    participant Rv as Reviewer
    participant API as RepoMind API
    participant DB as PostgreSQL
    participant GH as GitHub

    Rv->>API: POST /review-runs/{id}/decision {decision, comment}
    alt decision = APPROVE
        API->>DB: save human_review (APPROVE), pinned to head_sha
        API->>API: evaluate merge_policy (1 human approval + CI green + AI clean?)
        alt policy satisfied AND auto_merge enabled for repo
            API->>GH: POST review (APPROVE) using Rv's token
            API->>GH: PUT /repos/.../pulls/{n}/merge using Rv's token
            GH-->>API: merge result
            API->>DB: pull_request.status = MERGED, log AutomationAction
        else policy not satisfied
            API-->>Rv: "approved, waiting on: [CI / more approvals]"
        end
    else decision = REQUEST_CHANGES
        API->>GH: POST review (REQUEST_CHANGES) using Rv's token, with comment
        API->>DB: pull_request.status = CHANGES_REQUESTED
        API-->>Rv: developer notified
        Note over GH,DB: developer pushes new commit → head_sha changes
        GH->>API: webhook: pull_request synchronize
        API->>DB: mark review_run STALE, pull_request.status = OPEN
        API->>API: re-run AI review automatically → classify NEW/PERSISTENT/RESOLVED
        API-->>Rv: re-review requested
    else decision = REJECT
        API->>GH: POST review (REQUEST_CHANGES) or close PR, per repo policy
        API->>DB: pull_request.status = REJECTED, log final decision
        API-->>Rv: PR closed, no further auto re-review unless reopened
    end

Merge policy (configurable per project/repo by Org Admin):

  • Minimum human approvals (e.g. 1)
  • Require CI status = success
  • Require latest AI review to have zero HIGH/CRITICAL findings unresolved
  • Require head_sha of approval == current head_sha (prevents "stale approval merges")
  • Merge method: merge / squash / rebase

If any condition fails, PUT /organizations/{org_id}/merge-policy blocks the automatic merge step and the PR sits as "Approved, blocked on policy" until satisfied — the reviewer can still manually call POST /pull-requests/{id}/merge to override, which is itself an audited action.

Reject vs Request Changes — why they differ: REQUEST_CHANGES expects the developer to push more commits and loop back into review. REJECT is a terminal decision (e.g. "we're not doing this at all") — no automatic re-review is scheduled, and reopening requires an explicit POST /pull-requests/{id}/reopen.

8. PR Chat — full context + history

  • POST /chat/sessions {pull_request_id} — creates a session pinned to the PR's current head_sha, findings, lint output, and top-k retrieved repo-rule chunks at creation time.
  • POST /chat/sessions/{session_id}/messages — every message is answered using: the pinned diff, the findings from the latest review_run, retrieved repo docs, and the conversation history so far.
  • GET /chat/sessions?pull_request_id= — list all past sessions for a PR (so switching between an "old" and "current" sha's chat context is visible).
  • GET /chat/sessions/{session_id}/messages — full message history for one session.
  • If the PR gets a new head_sha, old sessions are labeled (stale sha) in the UI but remain readable — a new session is recommended, not forced.

10. What Each UI Page Should Show

Repository page: name, default branch, connected date, last synced timestamp, open PR count, branch list (name, ahead/behind, last commit), recent commits (sha, author, message, date), repo-level risk trend (not per-developer).

PR detail page: title, author, head/base branch, status badge (OPEN / CHANGES_REQUESTED / APPROVED-BLOCKED / MERGED / REJECTED), commit list on this PR, files changed with diff stats, CI check status, AI review panel (findings grouped by severity, each tagged NEW/PERSISTENT/RESOLVED), conflict warnings against other open PRs, approval history (who, when, which sha), "Chat about this PR" panel, full event timeline.

Security page (org-wide): all open findings across repos, filter by severity/repo/status, accept/reject/ignore action per finding — this is a security-finding tracker, explicitly not a developer scoreboard (per your anti-goals).

Settings page: merge policy config, GitHub identity link status, webhook health, member/role management (Org Admin only).

Summary of the key corrections to implement

  1. Add POST /organizations — don't fold org creation into bootstrap.
  2. Replace approve with a decision endpoint supporting three outcomes.
  3. Add a separate merge endpoint + configurable merge policy; auto-invoke it only after policy checks pass.
  4. Drop any GitHub App plan — use per-user OAuth tokens for every GitHub-side action, so RepoMind never acts as an impersonal bot.
  5. Add branch/commit/file-level endpoints for the PR and Repository UI.
  6. Add chat session listing + history endpoints, pinned to head_sha.
  7. Add a real Security Findings endpoint set, explicitly distinct from any per-developer scoring (which stays prohibited).
